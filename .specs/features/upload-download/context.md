# Upload and Download Context

**Gathered:** 2026-09-26
**Spec:** `.specs/features/upload-download/spec.md` (this repository), plus the same feature in `fiap-x-api` and `processing-catalog`
**Status:** Ready for design

---

## Feature Boundary

S6 replaces "tell the API a storage key" with the product's real flow: an authenticated user uploads a video straight to object storage through short-lived presigned multipart URLs issued by the API, confirms the upload idempotently — which creates the Processing Request — and later downloads the ZIP through a short-lived presigned URL issued only to the owner of a completed request. It closes S5's known risk: the source key is generated by the API under the owner, never supplied by the client.

Already fixed by `docs/foudation.md` and not re-discussed: MP4 and MOV only, 500 MB maximum; multipart upload and download through short-lived API-issued presigned URLs; a mandatory `Idempotency-Key` on confirmation; the request is created at confirmation; only the owner (`sub`) uploads and downloads; the API never returns a storage key as data; the API pre-validates extension, MIME type and declared size, and the Worker validates the real content; binaries expire after 7 days.

## Implementation Decisions

### Upload contract

- `POST /uploads {fileName, contentType, sizeBytes}` → `{uploadId, partSize, parts: [{partNumber, url}], expiresAt}`. `uploadId` is opaque to the client.
- Parts are 16 MiB (at most 32 for 500 MB).
- Confirmation: `POST /uploads/:uploadId/complete` with the `Idempotency-Key` header and no body. **The API lists the uploaded parts in storage itself**; the client never sends ETags.
- **A real size different from the declared `sizeBytes` is rejected at confirmation** (400); the upload is discarded and no request is created. This keeps the 500 MB limit from being decorative.

### Idempotency-Key

- Required on confirmation; missing → 400.
- Scoped per user: the same string from two users is two keys.
- Same key, same upload → the same Processing Request again.
- **Same key reused for a different upload → 409.**
- **Remembered for as long as the Processing Request exists** — stored with it in the Catalog, unique per owner. No purge job; a late retry can never create a duplicate.
- Concurrent confirmations with one key create exactly one request. A key is consumed only once a request exists; a failure before that leaves it unused.

### URL lifetimes (configurable; these are the defaults)

- Upload part URLs: **1 hour**.
- Download URL: **5 minutes**; a new one on every request, after re-authorizing the owner.

### Download and the old endpoint

- `GET /processing-requests/:id/download` → `200 {url, expiresAt}` (JSON, not a redirect).
- A request that is not `COMPLETED` → 409; another owner's or a missing one → 404, identical to S5's.
- **`POST /processing-requests {sourceStorageKey}` (S5) is removed.** Creation happens only through upload + confirm. The platform's seed script and smoke move to the real flow.

### Agent's Discretion

- Source keys are `sources/<sub>/<uuid>.<ext>`, generated by the API.
- An upload started and never confirmed is discarded by the bucket's own lifecycle rule for incomplete multipart uploads (1 day); nothing to clean up by hand.

### Declined / Undiscussed Gray Areas → Assumptions

None declined; all four areas were discussed.

## Deferred Ideas

- Cancelling an upload explicitly (`DELETE /uploads/:id`) — the lifecycle rule covers abandonment; an explicit cancel is a separate capability.
- Resuming an interrupted upload across part-URL expiry — out of scope; the client starts a new upload.
- Sharing a ZIP with another user, reprocessing — out of scope in the gap analysis.
