# Real Media Processing Specification — platform

## Problem Statement

The Worker announces that it processed a video without processing one. `AcceptAllVideoValidator` accepts every file without opening it, and `DeterministicFramePackager` returns a storage key without producing a package. The lifecycle, the persistence and the events are all real; the media is not. This slice gives the Worker somewhere to read a real video from and somewhere to put a real ZIP, and makes the local smoke prove that a ZIP with the right number of frames actually came out.

This repository owns the part that is topology, not media: the object storage, its bucket and retention, the fixture that seeds a real video, the CPU limits that the Worker's thread count has to match, and the smoke that asserts the outcome.

## Goals

- [ ] S3-compatible object storage in the local topology, with a private bucket the Worker can read and write
- [ ] Source videos and ZIP packages expire after 7 days, as `docs/foudation.md` requires
- [ ] A real MP4 reaches the Worker without waiting for the upload path (S6), through a versioned fixture and a seed script
- [ ] The smoke fails when the ZIP is missing, empty, or carries the wrong number of frames — not merely when a status never arrives
- [ ] The Worker's container CPU limit and its FFmpeg thread count are set in one place, so they cannot drift apart

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
| --- | --- |
| Presigned upload and download URLs | S6. The API issuing short-lived URLs is a contract and authorization concern; this slice only needs bytes to exist at a key |
| Provisioning storage in the cluster | S9a owns the Kubernetes manifests. Compose is the target here |
| Frame extraction itself | `processing-worker`. This repository provides the storage, the fixture and the assertion, not the FFmpeg invocation |
| Owner-scoped access to objects | S5 introduces the authenticated owner. The bucket is private to the services; per-user authorization has no subject yet |
| Retention enforcement by a scheduled job | The bucket's own lifecycle rule is the mechanism. A cron that deletes objects would duplicate what the storage already does |

| Assumption / decision | Chosen default | Rationale | Confirmed? |

## User Stories

### P1: Object storage in the local topology ⭐ MVP

**User Story**: As the Worker, I want a private S3-compatible bucket in the local topology so that I can read the source video and store the ZIP I produce.

**Why P1**: Without it the Worker has nowhere to read from and nowhere to write to, so no part of this slice can be demonstrated.

**Acceptance Criteria** (each line is one EARS pattern):

1. WHEN the topology starts THEN the stack SHALL expose an S3-compatible object storage service that reports healthy before the Worker starts.
2. WHEN the storage service becomes healthy THEN the stack SHALL ensure a bucket named `fiapx` exists.
3. The bucket SHALL deny anonymous access, so that an object is reachable only with credentials.
4. WHEN the bucket already exists THEN the bootstrap SHALL complete successfully without altering it.
5. WHERE object storage credentials are required the stack SHALL supply them through environment variables rather than any file committed outside the Compose definition.

**Independent Test**: Start the stack, confirm the storage service is healthy and the bucket exists, and confirm an unauthenticated request for a known object is refused.

---

### P2: Retention that the product rule requires

**User Story**: As the operator, I want stored objects to expire after 7 days so that the system honours the retention rule without anyone remembering to delete anything.

**Why P2**: The bucket is usable without it, so it does not block the demo — but it is a stated product rule, and it is cheapest to configure beside the bucket it governs.

**Acceptance Criteria**:

1. WHEN the bucket is created THEN the stack SHALL configure a lifecycle rule expiring objects 7 days after creation.
2. WHEN the bootstrap runs against a bucket whose lifecycle rule is already configured THEN it SHALL leave the existing rule in place and report success.
3. The lifecycle rule SHALL apply to both the `sources/` and `zips/` prefixes.

**Independent Test**: Start the stack and read the bucket's lifecycle configuration back, confirming a 7-day expiry covering both prefixes.

---

### P3: A real video, seeded

**User Story**: As a developer running the smoke, I want a real MP4 to exist at a known key so that the Worker can be exercised before the upload path exists.

**Why P3**: It exists only to unblock the demonstration until S6 replaces it. It is deliberately the first thing to be deleted rather than maintained.

**Acceptance Criteria**:

1. WHEN the seed script runs THEN it SHALL place a readable MP4 in the bucket under the `sources/` prefix and SHALL print the resulting storage key.
2. WHEN the seed script runs twice THEN it SHALL leave exactly one object at that key.
3. IF the object storage service is unreachable THEN the seed script SHALL exit non-zero with a message naming the service, rather than reporting success.
4. The fixture SHALL state its own duration and frame rate where it is defined, so that the expected frame count is derivable rather than guessed.

**Independent Test**: Run the seed script against a running stack, then list the bucket and confirm one readable object whose duration matches the declared fixture.

---

### P4: The smoke proves a ZIP, not a status

**User Story**: As a reviewer, I want the local smoke to fail when no real ZIP came out so that a green run means frames were actually extracted.

**Why P4**: The current smoke asserts that a status reached `COMPLETED`. Every implementation in this slice could be a stub and it would still pass — which is precisely how the previous slice shipped a complete, unreferenced persistence layer.

**Acceptance Criteria**:

1. WHEN the smoke completes THEN it SHALL download the object at the `zipStorageKey` the Catalog reports and SHALL assert the archive is readable.
2. WHEN the archive is read THEN the smoke SHALL assert its entry count equals the fixture's duration in seconds at 1 frame per second.
3. IF the archive is absent, unreadable, or empty THEN the smoke SHALL exit non-zero and SHALL say which of the three it found.
4. WHILE the smoke is running it SHALL leave no downloaded artefact behind after it exits.

**Independent Test**: Run the smoke end to end and confirm it reports the frame count; then point `zipStorageKey` at a missing object and confirm it fails with the absence named.

---

### P6: The smoke proves a rejection, across every service

**User Story**: As a reviewer, I want the local smoke to drive one request to `FAILED` through the real services so that the failure path is proven the same way the success path is.

**Why P6**: S2's "done when" asked for a request reaching `FAILED` by validation rejection through the running system. The S1–S3 verification (2026-09-24) found it proven only against a fake broker inside the Catalog, because the Worker could not reject anything. This slice is the first in which it can, so it is where the proof belongs.

**Acceptance Criteria**:

1. WHEN the smoke runs THEN it SHALL seed, alongside the valid fixture, an object that is not a video, and SHALL create a second request naming it.
2. WHEN that request settles THEN the smoke SHALL assert its status is `FAILED` and its `failureReason` is the safe text mapped from `FORMATO_INVALIDO`.
3. WHEN that request settles THEN the smoke SHALL assert that no archive exists for it and that Notification recorded exactly one delivery for its terminal event.
4. IF the request reaches `COMPLETED` or stays non-terminal past the smoke's timeout THEN the smoke SHALL exit non-zero and SHALL name the status it observed.

**Independent Test**: Run the smoke and see both requests settle, one `COMPLETED` with an archive and one `FAILED` with the safe reason; then bind the Worker back to `AcceptAllVideoValidator` and confirm the smoke fails naming `COMPLETED` where `FAILED` was expected.

---

### P5: CPU limit and thread count set together

**User Story**: As the operator, I want the Worker's CPU limit and its FFmpeg thread count to come from one place so that they cannot drift apart.

**Why P5**: FFmpeg reads the host's core count, not the cgroup's. On a 32-vCPU machine with a 2-CPU limit it opens 32 threads and is throttled by the scheduler — slower than if it had opened two. AD-006 fixed the rule; nothing yet enforces it.

**Acceptance Criteria**:

1. The Worker service SHALL declare an explicit CPU limit in the Compose definition.
2. WHEN the Worker starts THEN the stack SHALL pass it a thread count derived from that same CPU limit.
3. IF the declared CPU limit and the configured thread count disagree THEN the topology check SHALL fail and SHALL name both values.

**Independent Test**: Read the Compose definition and confirm the limit and the thread count agree; change one and confirm the check fails naming both.

## Edge Cases

- IF the storage service is healthy but the bucket bootstrap fails THEN the stack SHALL surface the failure rather than starting the Worker against a missing bucket.
- IF a stale storage volume from an earlier run holds a bucket without the lifecycle rule THEN the bootstrap SHALL add the rule rather than assume it is present.
- WHEN the smoke runs twice against the same stack THEN it SHALL create a distinct request each time and SHALL NOT assert against a ZIP from the previous run.
- IF FFmpeg is unavailable where the fixture is generated THEN the seed script SHALL fail with that named cause rather than uploading a zero-byte object.
- WHEN the topology starts on a machine with fewer cores than the declared CPU limit THEN the stack SHALL still start, and the thread count SHALL remain the declared value.

## Success Criteria

How we know the feature is successful:

- [ ] `docker compose up` yields a healthy storage service and a private `fiapx` bucket with a 7-day lifecycle rule
- [ ] The seed script places a readable MP4 and prints its key; running it twice leaves one object
- [ ] The smoke downloads the produced ZIP and asserts an entry count equal to the fixture's seconds of video
- [ ] Replacing the Worker's frame packager with a stub makes the smoke fail, and the failure names the missing or empty archive
- [ ] The Worker's CPU limit and thread count are read from one place, and a deliberate mismatch fails the check
- [ ] The same smoke run drives a non-video object to `FAILED` with the safe `FORMATO_INVALIDO` reason and one Notification delivery

## Dependencies

S3 (`durable-persistence`) is merged, and this branch was rebased onto it on 2026-09-24: the Compose topology it extends includes PostgreSQL, and the smoke it extends already reaches `COMPLETED` through a durable Catalog.

`fix/pre-s4-hardening` merged on 2026-09-25 (`fiap-x-platform#5`, `processing-catalog#6`, `notification-service#6`), and this branch was rebased onto it the same day. It changed what this slice extends:

- **V2 resolved (AD-012)** — `rabbitmq/definitions.json` now declares every traffic queue and its `.dlq` as quorum queues under a dead-letter policy with `delivery-limit: 5`. This slice does not touch the broker; a rejected or poisoned job in the smoke lands in a DLQ where it can be inspected.
- **V3 resolved (AD-013)** — the Catalog applies lifecycle events under a row lock and tolerates their order, so a fast extraction of the 8-second fixture cannot strand a request in `PROCESSING`. A red smoke points at the media path. Proved by 10 consecutive green smoke runs on the hardened stack.

One finding still bears on this smoke and is not fixed by this slice:

- **V11** — the CI `integration` job skips itself when `SERVICES_READ_TOKEN` is absent and still reports success; it did exactly that on `fiap-x-platform#5`. Until that changes, this smoke is proved only by running it locally.
